# Catalog-owned knowledge publication and coverage

Status: implementation of the accepted [P4 design, issue #278](https://github.com/LeonJoeeee/papervault/issues/278) and [P5a extraction registration, issue #282](https://github.com/LeonJoeeee/papervault/issues/282); activation requires the evidence and writer handoff below.

## Context

The ledger, LightRAG document status and library previously described different units and could disagree about completion. A processed backend document does not establish which input or recipe produced it, whether publication was accepted, or whether every required output remains available. P4 executes the constitution and refactor plan recorded in [ADR-0007](0007-papervault-constitution.md). It shares its publication primitives with P5; this slice does not implement backup or garbage collection.

## Decision

Postgres catalog commands own typed units, immutable input manifests and recipes, logical jobs and appended attempts, publication receipts, generation manifests and version selections. Execution, achieved tier, quarantine, publication and observed availability are separate dimensions. Stable operation IDs make committed commands replayable; optimistic revisions, database leases, authority epochs and monotonically increasing fences reject stale mutations. Outbox delivery preserves the attempt's submission identity and conservative accounting after an ambiguous external outcome.

Inputs are captured into immutable, content-addressed files under the configured knowledge store before admission. Artifact hashes and byte lengths describe the consumed bytes; the library's catalog revision remains a separate concurrency guard. Section mappings bind the exact parent evidence and segmentation revision. An expected inventory chooses whole-document or required-section coverage without counting both.

LightRAG's existing extraction, merge, deletion, embedding and query algorithms remain in use. Each attempt writes private deltas over a pinned logical aggregate. Postgres KV/vector and Neo4j graph adapters resolve the latest replacement row across the pinned layers before retrieval or traversal. Durable tombstones mask inherited deletions; replacement summaries come from the existing LightRAG reducers. This preserves shared entities and cross-document graph paths without allowing an unpublished contribution to alter the served aggregate. Model-specific vector tables require prepared backend schema. Runtime connection acquisition must not run LightRAG's legacy schema migrations.

A recoverable sealed receipt binds the submission, attempt, fence, unit, input, recipe, generation, aggregate base and verified output inventory. Publication rechecks that base and current eligibility before atomically registering lineage, publication history, selections, a new manifest, audit and downstream work. A conflicting aggregate base requires a new admitted attempt; it cannot append an unrebased delta. Candidate publication never moves production. Promotion checks a complete candidate against current requirements. Durable staging, recovery and reader pins protect namespaces across these transitions; no GC is activated here.

Recovering a sealed receipt consumes no execution admission slot. A completed receipt awaiting a new aggregate base therefore leaves capacity for its rebase claim and subsequent queued jobs; the new attempt still receives its own submission identity, fence and capacity reservation.

Before sealing, the adapter verifies each document's discovery indexes against its graph contribution, derived independently from private graph sources and uncapped entity/relationship chunk memberships. Membership-only changes count even when a source limit causes the original reducer to skip a graph write. The receipt retains the document, chunks, entity IDs and relationship pairs. A missing index is verified empty only when the corresponding contribution is empty; graph rows rebuilt solely for other documents do not become successor contributions.

Physical backend receipts carry a versioned document-index verification attestation bound to their exact retired receipt set. The shared catalog receipt validator enforces it during sealing, completion and publication, including recovery of an already sealed submission. Full-text and abstract receipts also bind the contribution evidence to the document identity and index inventory. Earlier physical receipts without this protocol remain immutable history, but cannot receive new completion/publication acceptance; they need an isolated verified rebuild. Metadata retirement receipts require the attestation too, so recovery cannot bypass retirement verification.

Retirement requires a successful deletion and operation-attributed rebuild history from the pinned LightRAG workspace. A success status alone is insufficient: failed entity/relationship rebuilds, unavailable extraction caches, parsing failures and unverifiable history prevent sealing and produce a discrepancy and repair request. `not_found` also fails validation because absent document status does not prove that inherited graph summaries or vectors no longer contain the contribution. Failed private deltas remain protected by recovery pins and are fenced from further writes or sealing; they never become selected aggregates.

Retirement commits a single-use delivery identity before any deletion mutation. An unsealed attempt that has started retirement cannot be resumed by another delivery, even within its original lease. The scheduler records the failed attempt, acknowledges its delivery, preserves uncertain charges and recovery pins, and requests an isolated rebuild. A genuine failed execution spends one failure-streak event; repeated delivery spends none. Recovery executes only in a fresh admitted attempt/namespace against the selected aggregate. Already sealed receipts remain recoverable after a lost commit response.

Every affected surviving entity and relationship vector must match the graph's canonical embedding content, endpoint identities and source chunks. Verification checks both relationship orientations, absent outputs and vectors left behind after graph deletion. It runs after the original retirement reducer and again over final private graph outputs before sealing. Retirement receipts bind a versioned graph/vector attestation to the retired receipt set and graph inventory digest; earlier retirement receipts lacking it cannot receive new completion/publication acceptance.

Before invoking deletion, the adapter checks the pinned document-status chunk set and both discovery indexes against the retired receipt's immutable contribution evidence. Missing or incomplete discovery cannot be interpreted as successful removal. Historical receipts without that evidence require an isolated verified rebuild; mutable backend indexes cannot manufacture the missing historical proof.

Retirement also validates the original reducer's inputs: every remaining chunk must have attributable extraction cache evidence, and each affected entity or relationship must have a description after the original source-limit selection. Partial caches, empty normalized summaries (including cache hits) and fallback paths that retain inherited descriptions are unverified. A context-bound adapter delegates to the unchanged reducer after validation and preserves typed build pauses that its workers otherwise swallow. Peak/breaker pauses take the catalog deferral path instead of creating a retirement failure or repair.

Vector-producing recipes bind a generation to an immutable embedding contract. Model identity, dimensions and embedding implementation must remain compatible across its aggregate. A model change needs a new generation; serving refuses to query an older generation with a different configured embedder. Other recipe changes retain their own exact logical job identities and explicit desired mappings. Effective recipes also include the LLM wrapper's loaded token ceiling, transport/retry settings and gateway mode; recording loaded values avoids claiming environment changes that the running wrapper has not adopted.

Serving pins one exact catalog manifest before retrieval, graph traversal, aggregation and cache access. It refuses a mixed aggregate containing an ineligible selected contribution rather than exposing its effects through another document. Eligibility and the serving pointer are checked again before returning a response. Direct legacy graph writers are rejected after authority handoff.

Backend collectors record nonauthoritative, identity-qualified observations. A processed document status alone cannot heal a job. Missing or corrupt published material retains its history and creates deduplicated repair work. Repair rebuilds use an isolated candidate, admitted only in the operator's monthly reboot window of at most two hours; promotion remains an explicit command.

The catalog-only coverage read performs no refresh or repair. A complete result needs the exact selected publication, compatible input/recipe/inventory and fresh positive verification for every required output. The default observation age is 300 seconds, based on backend observation time. Verified empty graphs require explicit evidence and applicable byte proofs. Unknown provenance, missing identity and stale observations receive no completeness credit.

## Consequences and activation

### Extraction registration (P5a)

Extraction uses the artifact branch of `publish_derivation`. A completion captures the exact input bytes, metadata and typed record identity before local transformation, together with a canonical recipe containing code hashes, package/configured model identity, loaded transport/retry and gate settings. Firecrawl's observed raw markdown is the input boundary; undisclosed source-page bytes, remote engine version and actual serving model remain explicitly unknown. Existing outputs without execution evidence remain `legacy_unknown`; recovery never manufactures their recipes.

Inputs are installed without replacement at `extracts/inputs/<sha256>`. A completion directory contains `output.md` and `completion.json`; file readback, file fsync, directory fsync and atomic directory rename precede registration. Its generation is `extraction:<completion_id>`, independent of graph generations. The receipt binds hashes, byte lengths, exact immutable locators, tier, input and recipe digests, original catalog revision/authority epoch and predecessor guard. Receipt validation checks these identities against the retained bundle. Later extraction preserves older versions. Conventional `extracts/md/<key>.md` files remain disposable compatibility projections, and rejection never deletes an immutable version.

The [orchestrator ruling](https://github.com/LeonJoeeee/papervault/issues/282#issuecomment-6309623189) permits legacy and standalone JSON extraction to succeed with this durable pending bundle. Pending is a retained evidence disposition, not catalog publication or conforming coverage. Under committed catalog authority the shared writer transaction adds an append-only extraction receipt and derivation, an extraction registration audit, a predecessor/revision fence and one distillation outbox item before reporting success. It creates no distillation attempt, graph publication or graph selection. The additive schema migration is version 5 and remains an explicit administrative operation.

`registration-request.json` retains the exact operation payload for unknown-commit replay. Queue startup, per-key extraction recovery and catalog intake deliver retained evidence without repeating transformations, success/failure events or execution attempts. Stale revisions/epochs, changed inputs, conflicting predecessors and invalid evidence retain the bundle without credit. Recovery reports blocked completions without stopping unrelated queue work; catalog success shortcuts still require registration for selected new outputs. A crash after alias replacement but before record save recovers the same verified version.

Staged reopen execution records its original claim and live unit identity separately from verified metadata fills. Guarded writeback shares the existing record/claim transaction with registration. Refused and byte-identical staged outputs survive cleanup; ordinary queue recovery cannot publish a dispatched or expired staged result. Merge adoption moves the selected markdown path and provenance together. Intake authorizes an adopted receipt through the committed alias chain and keeps its original unit/derivation identity. A selected legacy pending origin may register through that chain only when the canonical record is eligible and selects that exact output. No historical catalog revision is invented.

Catalog distillation reads the verified immutable output and records its extraction derivation as upstream input. Outbox retries are delivery, not attempts; the consumer waits for committed record selection and acknowledges superseded inputs without admitting stale work. These changes do not activate catalog authority, implement coordinated backup/restore, garbage collection or research-asset deletion.

### Authority handoff

`PAPERVAULT_KNOWLEDGE_JOBS` defaults to `legacy`. Selecting `postgres` requires an already committed catalog authority epoch and Postgres library authority. The configuration flag cannot transfer authority. Legacy ledger methods remain readable for historical comparison; their writers and direct legacy backend mutation entry points fail after handoff.

Legacy imports preserve raw keys, states, timestamps and available counter semantics in quarantined, non-executable records. They do not fabricate historical attempts, inputs, recipes, publication or dispatch tokens. Durable change capture, aligned C0/C1 checkpoints, verified privilege revocation and backend worker fencing precede the authority transaction. Software rollback preserves catalog authority and accepted mutations. A reverse migration requires a separate design and rehearsal.

Source-row timestamps use one semantic form across C0 snapshots, exported journal images, planner comparisons and C1 freeze digests: UTC with significant fractional seconds and a `Z` suffix. Normalization is restricted to the ledger's `last_processed_at` timestamp; identities and other source text remain exact, and changed instants still fail old-image alignment. The durable capture journal retains its original PostgreSQL JSON evidence.

Resuming a pre-normalization C0 import verifies each source event's original literal hash before comparing timestamp semantics. Equivalent replay retains the accepted event bytes, hashes and projection encoding; new reports and final row digests use canonical timestamps. Prior report digests and row sets are independently verified before that comparison. Enrichment, older-checkpoint and independent-projection-change guards remain in force, including final handoff with unchanged historical rows.

Migration projections retain immutable accepted-plan lineage separately from source-event history. Whole-plan validation precedes mutation. Equal-source-version updates may enrich evidence or resolve an unverified mapping, but cannot discard a verified mapping or accepted disposition/observation evidence. Conflicting verified mappings fail explicitly while preserving quarantine. An interrupted older plan cannot replace a richer committed projection or checkpoint report; genuinely newer source versions remain eligible for projection changes.

Enrichment must use the current or a newer accepted source checkpoint. An older checkpoint cannot change a row projection while leaving the newer checkpoint's report in place, even if that row's source version did not change. Replaying an already committed operation remains idempotent.

Duplicate dispositions describe the aligned source state at each event's sequence: the entire C0 snapshot, then each atomic captured change. Resolving a duplicate through deletion records a new tombstone with `source_deleted`; it does not remove the duplicate evidence from unchanged C0 events. Final keyed reports retain those historical dispositions on each source identity's latest event, while the final row digest describes the live source set.

Peak-window and breaker pauses settle the current attempt as deferred and return its job to the queue without updating the failure-streak reducer. The command fences the private namespace and acknowledges its submission delivery atomically. Uncertain costs and recovery pins remain protected. Genuine failures and actual expired leases retain their failure and parking semantics.

The [P4 rehearsal procedure](../specs/2026-10-20-p4-knowledge-handoff.md) describes the administrative interfaces and required evidence. Dedicated Postgres and actual backend tests, real-material coverage differences and an independent review are activation requirements. Unit tests and schema definitions alone do not establish them. In particular, the layered vector query uses latest-row selection before similarity search; its query plan and latency at corpus scale require measurement before activation.

The current durable representation writes complete immutable manifest inventories and cumulative receipt mappings. Across many publications this has quadratic metadata growth, despite compact shared read projections. Structural sharing and corpus-scale storage/write measurements remain unresolved activation concerns; no capacity or maintenance-window performance is claimed by this implementation.
